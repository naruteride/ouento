# 클릭 영역과 실제 픽셀 비교

캐릭터의 투명 여백은 바탕화면의 다른 앱으로 클릭을 통과시켜야 한다. 제품은 현재 모델의 삼각형·UV·텍스처 알파를 CPU에서 샘플링한다. GPU 픽셀 읽기는 제품의 프레임·커서 경로에 사용하지 않는다.

## 합성 규칙

고정한 Cubism Framework 5-r.5/Core 06.00.0001의 그리기 순서를 따른다. 각 drawable의 마스크·불투명도를 적용하고, 중첩 offscreen의 자식을 먼저 합친 뒤 해당 그룹의 마스크·불투명도를 적용한다. 최종 알파가 0.05를 초과할 때 클릭 대상으로 처리한다. 개별 drawable이 이 값보다 희미해도 여러 개가 겹쳐 보일 수 있고, 나중의 Out 효과로 앞선 영역이 지워질 수 있으므로 중간에 판정을 끝내지 않는다.

소스 알파를 S, 대상 알파를 D라 하면 SDK의 알파 합성은 다음과 같다. RGB 색상 계산은 이 판정에 필요하지 않다.

| 모드 | 결과 알파 |
| --- | --- |
| Over | S + D − S×D |
| Atop | D |
| Out | D×(1−S) |
| ConjointOver | max(S, D) |
| DisjointOver | min(1, S+D) |
| AddCompatible·MultiplyCompatible 및 구형 Additive·Multiplicative | D |

마스크 입력 drawable의 표시 여부·표시 불투명도는 SDK의 마스크 생성과 마찬가지로 적용하지 않는다. 여러 마스크는 알파의 합집합이며 반전 마스크는 그 보수다. 손상된 순서·계층·마스크 메타데이터로 판정할 수 없으면 클릭을 통과시킨다.

## 재현 절차

1. README의 SDK 자산 준비와 Rust 검사를 완료한다.
2. `npm run test:compatibility`로 공식 샘플을 실제 가져오기 경로로 검사하고 개발용 자산을 만든다.
3. `npm run dev` 후 `http://127.0.0.1:1420/tests/browser/model-hit-check.html`에서 비교 버튼을 누른다.

검사기는 실제 제품 렌더러의 동일한 프레임에서 WebGL 픽셀과 제품 `hitTest`를 비교한다. Haru·Mao·Ren 기본 모습, Ren 재로딩, 디스플레이·홀로그램·노이즈 효과, 루트 그룹 불투명도 0을 합쳐 8개 상태를 검사한다. 효과 값은 기존 Core 갱신 직전에 적용하고 프레임당 갱신을 중복하지 않는다. 루트 그룹 0은 합성 경계 검사이며 자연 모션이 아니다. 제품의 자동 전신 모션을 추가하지 않으며 결과 페이지도 배포 빌드에 포함하지 않는다.

샘플 위치는 GPU 픽셀 중심이며 세로축을 모델 좌표로 변환한다. 픽셀 알파 12 이하에서 hit이면 raw false positive, 12 초과에서 miss이면 raw false negative로 센다. 반올림·경계 차이를 구분하기 위해 3×3 이웃의 최대 알파가 2 이하인 투명 영역과 최소 알파가 128 이상인 불투명 영역의 오판도 따로 센다. 붉은/푸른 점은 후자의 명확한 오판이다. 한 프레임의 희소 격자 검사이며 모든 픽셀·모든 모델 동작의 일치를 보장하지 않는다.

## 2026-09-22 측정

macOS 26.6.2 arm64, Chrome 152 기반 In-app Browser, CSS canvas 300×400·DPR 2에서 상태당 3,350개씩 총 26,800개 표본을 검사했다. 기존 코드의 임시 복사본과 수정 코드를 **같은 GPU 프레임**에서 비교했다. [자산·코드 해시와 측정값](model-hit-testing-2026-09-22.json)에 기록했으며 최종 검사기는 임시 복사본에 의존하지 않는다.

| Ren 상태 | 수정 전 명확한 투명 영역 오판 | 수정 후 |
| --- | ---: | ---: |
| 홀로그램 | 2,532 | 0 |
| 노이즈 모션 끝부분의 효과 값 | 2,445 | 0 |
| 루트 offscreen 불투명도 0 | 636 | 0 |

8개 상태 모두 수정 후 명확한 투명·불투명 영역 오판과 WebGL 오류는 0이었다. 경계 기준의 raw 오판은 상태별 false positive 0~9개, false negative 0~6개가 남았다. 이 값은 아래 래스터 근사 한계와 구분해 기록하며 완전한 픽셀 일치로 보고하지 않는다. 저장한 비교 시간에는 이전 코드의 CPU 판정도 포함되므로 제품 단독 성능 수치가 아니다.

구형 Haru·Rice의 정상 Core 보간에서 불투명도 `1.0000499487`이 나오는 것을 확인해, 유한 값은 0..1로 보정하고 NaN·Infinity는 계속 거부한다. 자동 회귀에서도 실제 Haru 값을 사용했다.

검사 중 Ren을 연속해서 불러오면 삭제된 framebuffer를 다시 바인딩하는 SDK 캐시 문제가 재현됐다. 이 앱은 canvas당 모델 하나를 소유하므로 모델 해제 직후 해당 GL context의 offscreen 풀을 제거한다. 다른 canvas의 풀은 유지한다. 실제 SDK를 사용하는 회귀에서 재로딩 3회·중복 정리·다른 canvas 보존을 확인했고, 위 브라우저의 연속 Ren 로딩에서도 GL 오류가 사라졌다.

임시 비교 코드를 제거한 최종 검사기도 8개 상태를 다시 확인했다. 명확한 영역 오판·GL 오류가 0이었고 생성한 framebuffer 56개와 texture 65개가 종료 시 모두 해제됐다. 추적 핸들의 반환 결과이며 GPU 바이트나 네이티브 전체 메모리 측정은 아니다. JavaScript 테스트 49개·컨트롤러 시나리오 44개·TypeScript·포맷 검사와 macOS 개발용 앱 번들 빌드도 통과했다.

## 남은 차이

CPU 알파 텍스처는 긴 변 최대 1024픽셀로 축소한다. GPU 마스크의 별도 래스터 해상도·LINEAR 필터링, RGBA8 중간 버퍼 반올림, 삼각형 겹침과 공유 변 처리, MSAA는 CPU 추정과 차이가 있다. 특히 아주 희미한 경계는 검사 오차를 허용한 영역이다. 네이티브 창의 클릭 통과·포커스·드래그·혼합 DPI는 이 검사와 별도로 양 OS에서 확인해야 한다.
